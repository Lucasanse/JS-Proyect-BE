## Qué hace

Endpoints de administración para crear, editar, eliminar y desactivar productos. Un producto con ventas no se puede eliminar: el endpoint responde `409` y hay que desactivarlo, así no se pierde el historial.

Closes #35

## Cambios

### Productos (`/api/admin/productos`, solo rol ADMIN)
- `GET /` listado con búsqueda, filtro por categoría y estado (activos/inactivos/todos), paginado
- `GET /:id` detalle para editar
- `POST /` alta con validaciones (nombre, descripción, marca, categoría, precio > 0, stock ≥ 0)
- `PUT /:id` y `PATCH /:id` edición
- `DELETE /:id` elimina solo si no tiene ventas. Si tiene ventas, o está en una PC armada por un usuario, responde `409` con un mensaje que indica desactivarlo
- `PATCH /:id/estado` activar o desactivar
- `POST /imagen` subida de imagen (multipart, campo `imagen`): se guarda en `uploads/` y devuelve la URL pública

### Datos del formulario
- `GET /api/admin/marcas` marcas con las categorías donde tienen productos
- `POST /api/admin/marcas` crea una marca; si ya existe con otras mayúsculas devuelve la existente
- `GET /api/admin/tipos-componente` tipos con sus atributos técnicos y valores sugeridos

### Permisos
- Todo `/api/admin/*` pasa por `requireAuth` + `requireAdmin`: sin sesión `401`, sin rol admin `403`

### Catálogo público
- `/productos`, `/marcas` y `/productoDetalle/:id` muestran solo productos activos
- No se puede agregar al carrito un producto desactivado

### Base de datos (migraciones)
- `producto_activo`: campo `activo` (boolean, default `true`) en `Producto`
- `marcas_y_opciones_atributos`:
  - tabla `Marca`; `Producto.marca` (texto) pasa a ser `idMarca`. La migración mueve las marcas existentes sin perder datos
  - `AtributoTecnico.numerico` y `AtributoTecnico.opciones` (valores sugeridos)

### Componentes de PC
- El alta y la edición aceptan `componente: { idTipoComponente, wattsRequeridos, atributos: [{ idAtributo, valor }] }` o `null`
- Se valida que los atributos sean del tipo elegido y que los numéricos sean números

### Seed
- Categorías, tipos de componente y atributos se sincronizan siempre (upsert), aunque la base ya tenga productos
- 11 tipos de componente para PC gamer: CPU, GPU, RAM, Motherboard, Fuente, Almacenamiento, Gabinete, Cooler CPU, Refrigeración líquida, Ventiladores y Placa de red
- Categorías nuevas: Monitores, Gabinetes, Refrigeración, Conectividad, Sillas Gamer
- Productos de ejemplo para los tipos nuevos (solo se crean en una base vacía)

### Otros
- `errorHandler` responde `400` ante un JSON inválido y ante errores de subida de imagen
- Dependencia nueva: `multer`

## Cómo se guardan las imágenes

Las imágenes se guardan **en el disco del servidor del BE**, no en la base de datos ni en un servicio externo. En la base solo se guarda la URL (`imagenUrl`).

1. **En el formulario (FE):** el admin hace clic en el recuadro de la imagen, que abre un `<input type="file">` oculto, o arrastra el archivo encima (drag & drop nativo del navegador). No se usa ninguna librería.
2. **Validación en el FE:** antes de enviar se controla que sea una imagen y que no pese más de 5 MB.
3. **Envío:** el archivo se manda con `FormData` a `POST /api/admin/productos/imagen` apenas se elige, y se muestra "Subiendo..." sobre la vista previa.
4. **En el BE:** `multer` recibe el archivo, vuelve a validar el formato (JPG, PNG, WEBP, GIF o AVIF) y el tamaño, y lo guarda en la carpeta `uploads/` con un nombre aleatorio (por ejemplo, `3db7cafa-....png`) para que no se pisen dos archivos con el mismo nombre.
5. **URL:** el BE responde con la URL pública (`http://localhost:3000/uploads/xxx.png`), que el BE sirve como archivo estático. El formulario muestra la vista previa y esa URL se guarda en el producto al hacer clic en "Guardar".
6. **Limpieza:** si se cambia o se quita la imagen de un producto, o se elimina el producto, el BE borra el archivo del disco, siempre que ningún otro producto lo use.

También se puede **pegar la URL** de una imagen que ya esté en internet. En ese caso no se sube nada y se guarda esa URL tal cual.

⚠️ La carpeta `uploads/` está en el `.gitignore`: las imágenes subidas no van al repositorio, así que cada uno tiene las suyas en su máquina.
